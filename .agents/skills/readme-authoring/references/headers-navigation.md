# Headers and navigation

## Recommended opening

Use a readable project name, a concrete purpose statement, and useful next actions. A logo, banner, badge row, or demonstration may reinforce them. Keep names, descriptions, and essential links available as text.

There is no mandatory first-screen composition. A root README may need a maturity statement; a workflow README may need a prerequisite first. Do not force a showcase opening onto a narrowly scoped correction.

## Navigation decisions

Use short task-oriented quick links when they reduce searching. Add an explicit contents list when the page's length or structure warrants it; GitHub's generated outline is another valid route. Avoid duplicating a long outline without benefit.

Check anchors after renaming headings. Repeated headings receive distinct generated anchors. Punctuation, HTML, code formatting, and symbols can make guessed anchors unreliable. Prefer simple, unique headings and inspect local link consistency; state when renderer behavior was not checked.

## Example pattern

```text
Project name
Concrete purpose for a named audience
Quick start | Examples | Documentation | Contributing
Optional demonstration or compact status summary
```

This illustrates composition, not verified project wording or mandatory order.

## Avoid

- A banner as the only project name or explanation.
- Several screens of badge/share content before useful information.
- A table of contents that promises missing sections.
- Generic labels such as "click here" when a document title is clearer.

Compare [Rust](https://github.com/rust-lang/rust#readme) for concise routes and [Markdownify](https://github.com/amitmerchant1990/electron-markdownify#readme) for a branded opening. Their nomination or adoption does not prove a layout optimum.
