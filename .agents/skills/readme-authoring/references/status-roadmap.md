# Status, active development, and roadmap

## Required distinctions

| Status | Evidence needed | Do not imply |
| --- | --- | --- |
| Implemented | Current code and documented scope | Validated strategy quality |
| Software-validated | Specific checks and their coverage | All platforms, algorithms, or workloads verified |
| Experimentally measured | Reported experiment and conditions | Universal performance or convergence |
| Active development | Current project context | A promised release date or unsupported instability claim |
| Planned | Maintained roadmap or explicit user intent | Already available functionality |

The [progress log](../../../../docs/PLURIBUS_LOG.md) records dated work. Read relevant entries and the current implementation before changing maturity language. A skill reference must not freeze today's milestone as a permanent project identity.

## Recommended

Use a concise status paragraph or NOTE when it helps readers choose a workflow. It is acceptable to say the project is in active development. Name specific limitations close to the affected capability; avoid repeating a broad disclaimer in every section.

Example, subject to current evidence: "The software architecture is implemented; production-scale strategy quality remains unestablished." Do not change this into "all research is complete" or "nothing is usable." Both lose important distinctions.

## Roadmap

Link the maintained planning document or issue when one exists. Summarize only the milestones relevant to readers. Do not duplicate a large task tracker or invent dates to make the roadmap appear complete.

If current documents disagree, identify the concrete conflict and inspect supporting evidence. Correct only supported, in-scope claims; flag unresolved contradictions instead of choosing the most optimistic wording.
