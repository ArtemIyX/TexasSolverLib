# Style and accessibility

## Required

Use the repository's current communication rules. The default is plain technical prose, no decorative emoji, and no em dashes. Explicit user preferences can override project presentation defaults. Do not confuse a GitHub-rendered alert icon with authored decorative emoji.

Keep heading text meaningful without icons or color. Use descriptive links and informative alternative text. Important setup, limits, commands, and results must remain understandable without loading media. Do not communicate supported versus unsupported states by color alone.

## Recommended

Write concrete statements: name the capability, reader, or condition. Prefer "supports deterministic replay under the documented configuration" with evidence over an unqualified "fully deterministic." Keep short paragraphs and use tables for real comparisons rather than every sentence.

Use code formatting for commands, symbols, options, filenames, and machine output. Use bold sparingly for meaningful distinctions. Avoid all-caps section walls, repeated marketing slogans, decorative separators between every paragraph, and repeated disclaimer blocks.

Visual polish can come from consistent spacing, useful diagrams, a coherent banner, or a readable example. It does not require many images or centered body paragraphs.

## Rendering checks

When a rendered review is performed, inspect light/dark contrast, narrow width, table overflow, screenshot readability, and collapsed-section behavior. Do not report an accessibility audit based only on source review or four example screenshots from the research study.

## Example

Prefer a plain heading such as "Build requirements" over a row of tool icons that forces readers to infer compiler and CMake requirements. Icons may supplement a clear explanation when requested; they cannot replace it.
