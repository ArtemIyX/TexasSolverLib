# Support, contributions, and security routes

## Required

Use actual maintained channels. Verify repository identity before adding issue, discussion, email, or wiki URLs. Do not invent a Discord server, support address, vulnerability mailbox, or response-time promise.

Link the [contribution guide](../../../../CONTRIBUTING.md) for contributor workflow rather than copying its entire contents. Agent-oriented repository instructions are not a substitute for explaining how a human contributor begins.

Distinguish ordinary bug reports, questions, feature requests, and sensitive vulnerability reports where applicable. If a private security-reporting channel cannot be established, do not fabricate one or instruct users to post secrets publicly. State the specific missing route when necessary for the requested work.

## Recommended

Direct readers to a specific issue template or guide when useful and currently available. Describe what evidence makes a solver bug report actionable: configuration, reproducibility conditions, input/state, and expected versus observed behavior. Link detailed reporting requirements rather than expanding every category in the README.

For contribution guidance, make public-library, research, and compatibility boundaries easy to discover. Do not turn repository implementation rules into a long top-level product introduction.

## Example

"For contribution workflow and validation expectations, see the contributing guide." This is a useful route when the guide actually covers them. "Contact our security team at ..." requires a real channel and cannot be filled from a template guess.

Add sponsorship, maintainer recognition, and community links when real and relevant. They are optional presentation/community choices, not prerequisites for a technically sound README. Do not send messages or open issues as part of documenting the routes.
