# Information architecture

## Required

Keep purpose, the relevant starting path, and important qualification boundaries discoverable. Preserve technical meaning when condensing prose. If material moves, update in-scope incoming links and ensure the destination exists before linking it.

Do not convert a research solver into a marketing claim by removing necessary distinctions between software implementation and strategic validation.

## Choose a shape

- **Balanced root:** identity, purpose, current scope/status, a starting path, capabilities, deeper documentation, and contribution/legal routes.
- **Gateway:** a compact overview and specific routes into maintained documentation. Prefer this when substantial guides already exist.
- **Embedded guide:** a complete small workflow with enough requirements, commands, and output explanation to succeed without searching.

These are defaults, not fixed heading sequences. A migration notice or critical prerequisite can legitimately precede the overview.

## Tips

Use parallel headings that name actual tasks. A table is useful for comparing solver families or build choices. Prose is better for explaining why a boundary exists. Keep exhaustive parameter tables, derivations, benchmark histories, and large file inventories in their canonical documents when a short summary and link suffice.

Avoid retaining an outdated copy of a manual merely to make the README self-contained. Conversely, do not replace the only explanation of a required setup step with an unexplained generic homepage link.

## Example

Replace a long architecture chapter with a short verified pipeline and a descriptive link to the technical report, while preserving the root README's capability and limitation summary. Do not move material outside the user's authorized scope.

See [documentation and wiki](documentation-wiki.md) for choosing the maintained destination.
